# 项目设计经验总结 V4.0

> 记录的是“在本机真实库上验证过的做法与坑”，不是设计推演。
> 适用：竞驰管理通 → 管家婆财贸双全 / 辉煌 TOP15 的数据迁移工具，以及同类“旧库 → 商业 ERP”的直导工程。

## 一、五条设计原则

### 1. 一个源连接，两个目标引擎，不做两套界面

财贸与辉煌的写入方式完全不同（直写表 vs 官方过程），但用户的心智模型是“选目标 → 导入”。因此：

- GUI 只连一次源库，目标二选一；
- 引擎各自封装 `import_all()`，返回同构结果 `(项目, 结果, 明细)`；
- 字典、校验、导出共用同一套表格；
- 目标差异只体现在“目标页签默认值、徽标、目标名、可用模块”。

**收益**：新增目标不需要改界面；切换目标不会误连另一个源；交付只有一个 exe。

### 2. 能走官方过程就不要直写表

辉煌 TOP15 的基本信息不是“插一行”那么简单：过程会

- 生成合法树编号（纯数字、5 位分组、父子前缀）；
- 重算 `dsonnum/soncount/leveal`；
- 写权限串、刷新 `updatetag`；
- 校验重名、重号、条码占用。

自己拼 SQL 迟早在这些隐性约束上翻车。**唯一正确做法**：调用 `p_hh_BasicInsert*`，明细引用只取过程的 `OUTPUT g_tree/u_tree`。

### 3. “写进去”不等于“能显示”

本项目把验收分成两层：

- **写库层**：目标表有行、字段值对；
- **客户端读取层**：调用目标软件自带的 `xw_GetBasicData`，按模式读出来。

只有第二层通过，才能说“软件里能看见”。这也是本轮把“商品只回 1 行”“部门只有根行”抓出来的原因。

### 4. 幂等是导入工具的底线

同一批源数据重复执行，不允许产生第二条。做法：

- 每行写溯源备注 `竞驰ID:n`；
- 导入前按备注查重，命中即跳过；
- 编号/名称冲突只做“续排/加后缀”，不改源值。

部门模块第一次实测就是因为没有幂等，多出 `00002 业务部(竞驰)`；清理后补了“备注命中即跳过”。

### 5. 任何写库都必须可回滚

- 导入前整库 `.bak`（测试副本用 `COPY_ONLY`）；
- 隔离库被污染后不要“删行修”，直接 `DROP DATABASE` + `RESTORE ... WITH MOVE`；
- 目标已有真实数据时，不提供“清空重导”作为默认按钮。

## 二、架构决策与理由

### 2.1 为什么用“适配器 + 核心过程封装”两层

`gpj_kspc_adapter.py` 负责“业务编排”：读源行、算父子、去重、写备注、刷新标记；
`gpj_top15_core.py` 负责“协议”：连接、参数绑定、`rc` 错误码、事务提交/回滚。

这样做的原因：

- 官方过程参数多、类型严（varchar 长度、OUTPUT 位置），集中在一处最容易改；
- 业务规则（名称冲突加 `(竞驰)`、编号续排）可以独立测试；
- 换账套/换实例只改连接参数，不动业务。

### 2.2 为什么字典要“生成”而不是“手写”

手写字典会随目标版本漂移。正确做法是：

1. 读源库 `sys.columns`（104 表 / 1626 字段）；
2. 按映射规则生成；
3. 逐条到两目标库 `sys.columns` 实查，找不到标“目标缺列”；
4. 真实导入后按备注配对，逐字段回读；
5. 回读通过才定稿。

本项目用这个顺序抓出：财贸预收/预付真实列是 `PreARTotal00/PreAPTotal00`，不是想当然的 `YRTotal00/YPTotal00`；辉煌 `ptype` 根本没有 `unit1` 列。

### 2.3 为什么“期初”要分两套口径

- 财贸能同时承载“期初 100”和“当前结存 90”；
- 辉煌只有一套 `IniGoodsStocks`。

如果强行把两版本做成同一个数字，必然一边错。设计上明确：

- 财贸：`t_prime_goodsstock` → 期初；`t_base_goodsstock` → 当前；
- 辉煌：源无单据时，当前结存即期初。

**字典和报告必须写清“口径差异”，否则会被当成 bug 反复返工。**

## 三、编号体系：最容易翻车的地方

| 规则 | 财贸 | 辉煌 |
|---|---|---|
| 字符 | 数字串 | **必须纯数字**，含字母列表不渲染 |
| 层级 | 父编号 + 5 位序号 | 同左，但由官方过程生成 |
| 父子依据 | `parid` + 编号前缀 | **编号前缀**，不是 `parid` |
| 自定义编号 | 可保留源编号 | 过程会改写（`001→00102`、`1→101`） |
| 冲突 | 续排 | `rc=-1124`（编号或名称任一重复） |

工程结论：

1. 先让过程生成树号，再拿 `OUTPUT` 写明细，**不要预计算**；
2. 名称唯一化与编号唯一化是两件事，都要做；
3. 目标根行（`00000`）必须保留，`parid=00000`；
4. 改完必须 `updatetag=10000` + `xw_BaseUpdateTag=0`，否则客户端读不到增量。

## 四、验证方法论（五层）

### 第 1 层：无头冒烟

不弹 GUI，直接连真实库跑最小断言（表存在、过程存在、源行数、目标行数）。目的：排除连接/驱动/权限问题。

### 第 2 层：真实写入

在隔离副本上跑完整导入，记录每模块成功/失败数、生成的目标编号、耗时。

### 第 3 层：逐字段回读

按备注 `竞驰ID:n` 找到目标行，逐字段比对“源值 vs 目标值”。要区分：

- **真缺陷**：源值在目标没有业务等价物；
- **口径**：大小写、拼音、组合显示串、技术编号续排。

### 第 4 层：官方读取链路

调用目标自带 `xw_GetBasicData`，按 `B/P/K/E/D/A` 六模式读，确认导入行在“客户端会读到的结果集”里。

### 第 5 层：GUI + exe

- GUI 冒烟：切目标、改默认库、页签、状态栏；
- exe 冒烟：从 dist 产物启动，确认不是“源码能跑、包里没进去”；
- 交付包：逐文件 SHA256 比对，`PACKAGE_OK`。

**唯一可信的完成标准**：五层都过，且报告里能指到具体文件、行号、时间戳。

## 五、踩坑清单（按类别）

### 5.1 数据库/附加

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 同一 MDF 被实例 A 附加 | 实例 B `ATTACH` 报错误 32 | 先查 `sys.databases` 的物理路径，已附加则复用 |
| 跨服务账户访问目录 | 错误 5 | 备份/数据目录必须对 SQL Server 服务账户可写 |
| Express 不支持备份压缩 | `BACKUP WITH COMPRESSION` 失败 | 去掉 `COMPRESSION` |
| LDF 命名两种 | 找不到日志 | 同时探测 `<库>_log.ldf` 与 `<库>.ldf` |
| 隔离库删行 | 编号空洞、计数不对 | `DROP + RESTORE WITH MOVE`，不要手工修 |
| F 盘 Data 文件删不掉 | `os.remove`/`icacls` 全失败 | 先 attach 再 `DROP DATABASE` |

### 5.2 官方读取过程

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 辉煌第 5 参传 `OUTPUT` | 报 8162 | 5 参全普通实参 |
| 辉煌起止传 `1,200000` | 商品/部门只回 1 行 | **传 `0,0` 才是全量** |
| 财贸第 5 参不 `OUTPUT` | 报参数错误 | `DECLARE @o int; ... @o OUTPUT` |
| 辉煌 `@EtypeID` 传具体值 | 只回该分类 | 传 `''` 取全量 |
| 误以为权限过滤 | 行数不对 | 用 `p_hh_GetRightStr` 三种 `OperatorID` 实测，`@TableStr` 全空，排除 |

### 5.3 官方写入过程

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `rc=-1124` | 以为只是重号 | 编号或名称任一重复都会报；两套唯一化 |
| 过程改写自定义编号 | 明细引用错 | 只用 `OUTPUT g_tree/u_tree` |
| `p_hh_BasicInsertE_Commodity` 无 `@name` | 职员简称为空 | 插入后 `UPDATE employee SET ename=?` |
| `call_unit` 的 `@Bank/@BankAccounts` | 银行账号空 | 两个参数都要传 |
| 辅助单位换算率取 `unitrelation` | 100 变成 1 | 优先 `unitrelation2`，为空再回退 |
| 部门过程 `-1129` | 名称完全相同 | 名称加 `(竞驰)` 或先查重 |
| 条码 `UnitID` 写单位名 | `fn_GetBarCodeStr` 245，整块商品崩 | `UnitID` 必须是数字串 `'0'` |
| 部门无幂等 | 重复 `00002 业务部(竞驰)` | 先查 `dcomment='竞驰ID:n'`，命中跳过 |

### 5.4 源数据/字段

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 源 `name` 为空 | 目标简称空、界面空白 | `name` 为空回退 `fullname` |
| 源 `pym='1'` | 拼音码被写成数字 | 纯数字拼音占位不写 |
| 源 `goodsqty/price/total` | 不是 `Qty` | 按源真实列名，不套目标列名 |
| 辉煌 `stock` 用 `kusercode` | 写成 `ktusercode` 报错 | 以 `sys.columns` 实查为准 |
| 财贸 `Department` 八列 | 多写会报错 | `typeid/usercode/Comment/FullName/namepy/deleted/parid` |

### 5.5 GUI/打包

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `pack` 与 `grid` 混用 | 布局错乱 | 卡片标题独立 header 帧，body 只 `grid` |
| `StringVar` 未建全 | `KeyError` | `_defaults()` 先建全部变量 |
| tk scaling 随 125% 放大 | 界面撑爆 | 固定 scaling（96/72） |
| PyInstaller 丢 tkinter | exe 启动报错 | `--hidden-import tkinter --hidden-import _tkinter` + `--add-data tcl/tk` |
| 业务函数内 import 第三方库 | spec 静态分析看不到 | `hiddenimports` + `collect_submodules` |
| 长内联 Python | 中文/引号被截断 | 必须写 `.py` 文件再执行 |

## 六、反模式（明确不要做）

1. **不要用设计稿当数据字典**：必须生成 + 目标库实查 + 导入回读。
2. **不要用“目标表有行”证明成功**：必须走客户端读取过程。
3. **不要手工修隔离库**：删行会留空洞，直接还原。
4. **不要把“口径差异”当 bug**：拼音大小写、组合显示串、技术编号续排都是口径。
5. **不要在 worker 线程碰 tkinter**：日志走队列，主线程 drain。
6. **不要让密码进日志/文档/GitHub**：只从环境变量注入。
7. **不要用 27,000 字符级大块推 GitHub 文本**：会静默失真，必须 8,000 字符分片并回读 blob SHA。

## 七、交付前检查表

- [ ] 源库/目标库路径与日志一致，实例可连。
- [ ] 预检：源表、目标表、目标官方过程齐全。
- [ ] 导入前 `.bak` 已生成，路径可写。
- [ ] 导入结果 `fail=0`，每模块行数与源一致。
- [ ] 逐字段核对 0 不符（财贸 225、辉煌 119）。
- [ ] 官方读取 `B/P/K/E/D/A` 六模式，导入行可见。
- [ ] GUI 冒烟：切目标、默认库、页签正常。
- [ ] exe 冒烟：dist 产物可启动。
- [ ] 桌面包逐文件 SHA256 一致，`PACKAGE_OK`。
- [ ] 文档、字典、验证记录、README 的时间戳与内容同步。
- [ ] GitHub 文档与源码分片回读校验。

## 八、后续可做（未在本版实施）

1. **预演 diff**：导入前只读比对“将新增/将冲突/将跳过”，先审后写。
2. **行级差异报告**：源值/目标值/是否等价，导出 Excel 供客户签字。
3. **增量同步**：按源自增 ID 或更新时间水位，只导新增/变更。
4. **多账套批量**：多目标串行 + 汇总报告，每库独立备份。
5. **凭据安全**：DPAPI 保存连接串，密码不落日志。

这些都属于“锦上添花”，不影响 V4.0 已闭环的双目标直导与读取链路验收。
