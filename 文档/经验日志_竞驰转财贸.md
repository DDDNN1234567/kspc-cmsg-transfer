## 第 1 节：先确认“是不是同一个软件”

很多人会把“管家婆财贸双全（CMSQ）”和“管家婆辉煌 TOP”当成一套库。**不是。**

| 维度 | 辉煌 TOP | 财贸双全 CMSQ |
|---|---|---|
| 基础表 | `btype` / `ptype` / `C1Type` / `employee` | `Btype` / `ptype` / `Stock` / `Employee`（同名不同列集） |
| 价格载体 | `xw_P_PtypePrice`（3000+ 过程引用） | `T_Jxc_PtypeUnit`（135 个过程引用），`xw_*` 仅 3~5 个过程引用 |
| 期初 | `IniGoodsStocks` | `IniGoodsStocks` + 单据式 `DlyNdxIni/DlyIni` |
| 刷新 | `updatetag=10000` + `xw_BaseUpdateTag=0` | `UpdateTag=10000` + `XW_BaseUpdateTag=0` |
| 读基础资料 | `xw_GetBasicData @cMode,@nUpdateTag,@EtypeID,@beginRec,@endRec` | `xw_GetBasicData @cMode,@nUpdateTag,@nUsePage,@Rec,@OutRecords OUTPUT` |
| 客户/供应商 | 不同表或不同字段 | 同一 `Btype.isclient`（1 客户 / 0 供应商） |
| 仓库层级 | 必须平铺（类仓库挂不上库存） | 支持子仓（编号级联即可） |

**教训**：直接把辉煌版的经验（写 `xw_P_PtypePrice`、`xw_BaseUpdateTag=0`、仓库平铺）套到财贸，
数据会“写进去了但软件不认”。每次换目标产品，先读目标库的 `sys.sql_modules` 引用计数，确认主载体。

本次判定方法：

```sql
SELECT o.name FROM sys.sql_modules m JOIN sys.objects o ON o.object_id = m.object_id
WHERE m.definition LIKE '%T_Jxc_PtypeUnit%';
-- 135 个对象 → 主载体
```

## 第 2 节：两库不同实例，不能 `INSERT ... SELECT`

`SELECT name, physical_name FROM sys.databases` 一查就清楚：

- 源 `kspcDefault` 挂 `DESKTOP-8P5G8VQ\SQLEXPRESS`（SQL2008 Express SP4）
- 目标 `财贸测试demo` 挂 `DESKTOP-8P5G8VQ\SQLSERVER`（SQL2016）
- 本机没有默认实例，`localhost` / `.` / `(local)` 全部连不上

所以“直导”只能是：

1. Python 双连接 + 结果集搬运（本次采用，简单可控）；
2. linked server；
3. 导出脚本/中间库。

注意中文库名：pyodbc 连接串里直接写没问题；`sqlcmd -d` 要加引号；拼接动态 SQL 要 `[ ]` 包裹。

## 第 3 节：编号必须级联，且“重复导入不能漂移”

财贸与辉煌同源，客户端树按编号前缀构建：父编号 = 子编号去掉末 5 位。
所以 `00001` / `0000100001` / `0000200001` 这种形态是对的；连续编号会让明细挂不上分类。

**这次踩的坑**：工具是幂等的（按备注 `竞驰导入|%` 清理旧行再插入），但编号基线是在**清理之前**算的：

1. 第一轮导入 00001..00005；
2. 第二轮先算基线 → 看到 00005 → 从 00006 开始；
3. 再清理旧行 → 新数据变成 00006..00009，留下 00001..00005 空洞；
4. 第三轮继续漂移。

**修法**：算“目标已有最大编号”时排除导入行：

```sql
SELECT typeId FROM Btype
WHERE parid IN ('0','00000') AND typeId <> '00000'
  AND (Comment IS NULL OR Comment NOT LIKE N'竞驰导入|%')
```

修完后连续三轮导入编号都稳定在 00001 起。

**另一条**：顶级行的 `ParRec` 必须写**根记录的 Rec（通常是 1）**，不能写 0。
写 0 时树能显示但父引用链断，部分过程会按 `ParRec` 递归，出现“节点在、展开无子级”的假象。

## 第 4 节：期初库存的三张表别搞混

| 表 | 角色 | 谁写 |
|---|---|---|
| `IniGoodsStocks` | 期初库存（数量/单价/金额/批次） | 期初录入界面、`p_Jxc_ModifyIniGoodsStocks` |
| `GoodsStocks` | 当前库存快照（按仓库+商品+批次） | 单据过账、开账流程 |
| `GoodsStockscost` | 当前库存成本层（按期间） | 开账 `P_SC_SetInitOver`、成本计算 |

实测：

- `p_Jxc_GetIniGoodsStocks 'A','00000'` 读 `IniGoodsStocks`，能读回 100 / 100000 / 1000；
- `p_jxc_PkuCunList` 在会计期间为空时，`usesamecostmode=0` 走 `GoodsStockscost`，该表 0 行 → 库存状况显示 0；
- `V_Goodsstocks` 也不是直接读 `GoodsStocks` 的简单视图（本次写入 1 行后它仍返回 0 行）。

**结论**：期初写 `IniGoodsStocks`；若要求“库存状况”直接可见，还必须同时写
`GoodsStocks`（快照）与 `GoodsStockscost`（成本层）。本次最终交付按后者执行：

```sql
INSERT GoodsStocks(PtypeId,KtypeId,Qty,...) VALUES(...);
INSERT GoodsStockscost(PtypeId,Qty,Price,Total,GoodsOrder,KTypeID,Period,BlockNo)
VALUES(...,0,@k,@period,'');
-- Period 取 T_GBL_SysDataCW.Period（本次 200601）
```

写入后 `p_jxc_PkuCunList '00000','','',1,''` 读回 `QTY=100 / TOTAL=100000`，
“库存状况”与“期初库存”两个界面口径一致。

只写 `IniGoodsStocks` 适合“只做期初、等开账生成”的正式流程；演示/验收要求即时可见时，
写成本层更直接。两种口径不能混着解释，交付时要写清楚。

**官方写入语义**（照抄最稳）：

```sql
-- 成本算法 0/4
DELETE FROM IniGoodsStocks WHERE PtypeID=@p AND KTypeID=@k;
INSERT INTO IniGoodsStocks(PtypeID,KTypeID,Qty,Price,Total,GoodsOrder)
VALUES(@p,@k,@qty,@price,@total,0);
-- 且 Qty*Price 必须等于 Total，差额>0.0001 时用 Total/Qty 覆盖 Price
```

## 第 4B 节：“客户价格追踪”为空时先证明源里有没有

要求“客户价格追踪必须完整导入”时，不能只写一张空表就交差，也不能编数据。
正确做法是**把源库所有可能承载价格字段的表列出来逐张计数**：

```sql
SELECT t.TABLE_NAME, c.COLUMN_NAME
FROM INFORMATION_SCHEMA.COLUMNS c
JOIN INFORMATION_SCHEMA.TABLES t ON t.TABLE_NAME=c.TABLE_NAME
WHERE t.TABLE_TYPE='BASE TABLE'
  AND (c.COLUMN_NAME LIKE '%price%' OR c.COLUMN_NAME LIKE '%discount%')
```

本次结果（32 张相关表）：

| 表 | 行数 | 结论 |
|---|---|---|
| `t_base_price`（客户×商品×进价/售价/折扣） | 0 | 无客户价格 |
| `t_base_goodsprice`（商品价格方案） | 0 | 无价格方案 |
| `t_Client_Price_goods`（客户现价/原价） | 0 | 无客户价 |
| `t_base_goods_inner`（商品自带 40+ 价格列） | 2 | 两行商品，价格全 0 |
| 单据/促销/会员类价格表 | 0 | 无单据 |

结论：完整导入 = 0 行。工具仍实现四类映射（0005 进价 / 0007 售价 / 0006 进货折扣 /
0008 销售折扣），并在校验里比对“源可导行数 vs 目标行数”，源一旦有数据就能落库。

**教训**：交付“0 行”必须有这组计数证据，否则看起来像漏导。

## 第 5 节：往来单位的 `isclient` 是“能不能看到”的开关

财贸只有一个 `isclient`：

- `1` → 客户（`xw_GetBasicData 'C'`）
- `0` → 供应商（`'V'`）

竞驰 `t_base_wldw_inner.type`：0 商场专柜 / 1 普通客户 / 2 加盟代理 / 3 供应商。
本次按 `3 → 0`，其余 `→ 1`。验证时 `C=4、V=2`（各含根），与预期一致。

竞驰还有 `t_base_wldw_join`（“加盟代理:客户”）表示一个单位兼两个身份，
财贸 `Btype` **没有**这个字段。处理方式：

- 默认：不另建单位，把“兼客户”写进关联单位备注（否则客户列表出现重复的“加盟代理:客户”）；
- 可选：另建一条客户，`SettleBtypeId` 指向原单位。

两种都能跑，但默认选“不产生重复业务档案”。

## 第 6 节：备份与 pyodbc 的两个坑

1. **备份路径必须服务账户可写**：写 `C:\Users\...` 报“拒绝访问 错误 5”；
   写到 `F:\GraspServer\CMSQ\BackUp`（目标实例的数据目录旁）成功。
2. **SQL2008 Express 不支持 `BACKUP ... WITH COMPRESSION`**，去掉即可。
3. **pyodbc 执行 `BACKUP` 后连接变忙**：

```python
cur.execute("BACKUP DATABASE [db] TO DISK=N'...' WITH INIT")
while cur.nextset(): pass
cur.close()
# 之后才能 cn.autocommit = False，否则报
# "Connection is busy with results for another command"
```

4. **`BACKUP ... TO DISK=?` 参数化 + `WITH` 会语法错**（关键字 'WITH' 附近有语法错误 156）。
   `BACKUP` 的 `DISK` 参数不能像普通 DML 那样绑定，必须拼字面量并转义单引号：

```python
path_sql = path.replace("'", "''")
cur.execute(f"BACKUP DATABASE [{db}] TO DISK=N'{path_sql}' WITH INIT")
```

5. 旧实例不接受 `RESTORE VERIFYONLY ... WITH NO_INFOMSGS`，校验备份改用 `RESTORE HEADERONLY`。

## 第 7 节：sqlcmd 的输出坑（验证时别被骗）

- 输出是 GBK/CP936，PowerShell 直接读会乱码；用 `-o 文件` 再按 936 解码。
- `-W` 与 `-y/-Y` 互斥，一起用直接报错。
- 有时 stdout 只剩最后几行甚至为空，最稳的是 `-o` 写文件再读。
- 复杂查询建议直接用 pyodbc 脚本，`sqlcmd` 只用于一次性人工核对。

## 第 8 节：财贸的刷新与缓存

- 五张基础表 `UpdateTag` 统一 `10000`；
- `XW_BaseUpdateTag`（`BaseType, UpdateTag`）全部 `0`；
- 客户端缓存目录 `F:\GraspServer\CMSQ\Data\BaseInfo\<账套名>`；
  本次该目录**不存在**（账套可能未被客户端登录过），清缓存步骤提示“未找到”可忽略。

不要套用辉煌的 `Data\localData\<账套>-00000-*`。

## 第 10 节：本次结论

- 竞驰 → 财贸的基础资料、期初库存、结存库存直导已跑通，**32 项校验全绿**；
- 客户价格追踪按要求实现并校验：源库 32 张含价格字段的表逐张核对，
  `t_base_price`/`t_base_goodsprice`/`t_Client_Price_goods` 均 **0 行**，
  商品自带价格字段也全 0 → 完整导入结果是 0 行（能力已具备，源无数据）；
- 真正的“显示”验收标准是 `xw_GetBasicData` 的 B/C/V/P/K/E/D 返回行数、
  `p_Jxc_GetIniGoodsStocks` 读回期初、`p_jxc_PkuCunList` 读回结存；
- 财贸与辉煌的差异集中在**价格载体、期初/结存链路、往来单位分流、仓库层级**四处，
  换目标产品必须先重查这四处；
- 幂等导入的编号基线一定要排除“上一次导入行”，否则编号会一轮一轮往上漂。
